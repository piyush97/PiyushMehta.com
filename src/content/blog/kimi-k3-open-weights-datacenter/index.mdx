Moonshot AI just put one of the largest AI model checkpoints ever released on Hugging Face. You can download it without asking for API access, waiting for an enterprise contract, or trusting that a model provider will keep the same endpoint alive next year.

There is only one small problem: **the download is 1.56 terabytes**.

That number is not an estimate from a launch slide. I counted the 96 `.safetensors` weight shards in the [official Hugging Face repository](https://huggingface.co/moonshotai/Kimi-K3) and summed their published file sizes: **1,560,936,091,448 bytes**. On a connection sustaining a full 1 Gbps, the weights alone would take about three and a half hours to transfer. At 100 Mbps, the theoretical minimum is almost 35 hours. Storing the files is the easy part.

Kimi K3 has **2.8 trillion total parameters**, activates **104 billion parameters for each token**, supports a **1,048,576-token context window**, and uses native visual input. Moonshot's own deployment guidance recommends a supernode with **64 or more accelerators**.

So yes, Kimi K3 is open weight. No, it is not a laptop model.

That apparent contradiction is the most important part of this release. Kimi K3 does not put frontier intelligence on every desk. It changes who is allowed to operate it, preserve it, modify it, study it, and sell access to it. The gatekeeper moves from **permission** to **compute**.

This is not a hands-on model review. Launch-day API comparisons would be misleading without the same harness, reasoning budget, tool environment, and repeated runs. This is an evidence audit of what Moonshot released on July 27, 2026, what the architecture means, what the license permits, what independent evaluation has established, and why weights that almost nobody can run locally still matter.

## Kimi K3 at a glance

| Property | Kimi K3 |
| --- | --- |
| Architecture | Mixture of Experts (MoE) |
| Total parameters | 2.8 trillion |
| Activated parameters | 104 billion per token |
| Layers | 93 |
| Routed experts | 896 |
| Experts selected per token | 16, plus 2 shared experts |
| Attention layers | 69 Kimi Delta Attention + 24 Gated MLA |
| Context window | 1,048,576 tokens |
| Vision encoder | MoonViT-V2, 401 million parameters |
| Weight format | MXFP4 weights, MXFP8 activations |
| Published checkpoint | 96 shards, approximately 1.56 TB |
| Recommended inference engines | vLLM, SGLang, TokenSpeed |
| Official deployment guidance | Supernodes with 64 or more accelerators |

Sources: the [Kimi K3 model card](https://huggingface.co/moonshotai/Kimi-K3), [technical report](https://github.com/MoonshotAI/Kimi-K3/blob/main/k3_tech_report.pdf), and [technical blog](https://www.kimi.com/blog/kimi-k3).

## What Moonshot actually released

The headline is the full model checkpoint, but the release is larger than a directory full of tensors.

Moonshot published:

- the [Kimi K3 weights and model card](https://huggingface.co/moonshotai/Kimi-K3);
- a detailed [technical report](https://github.com/MoonshotAI/Kimi-K3/blob/main/k3_tech_report.pdf);
- a custom [Kimi K3 license](https://huggingface.co/moonshotai/Kimi-K3/blob/main/LICENSE);
- recipes for serving the model with [vLLM](https://recipes.vllm.ai/moonshotai/Kimi-K3), [SGLang](https://docs.sglang.io/cookbook/autoregressive/Moonshotai/Kimi-K3), and [TokenSpeed](https://lightseek.org/tokenspeed/recipes/models#kimi-k3);
- [FlashKDA](https://github.com/MoonshotAI/FlashKDA), MIT-licensed CUDA kernels for Kimi Delta Attention;
- [MoonEP](https://github.com/MoonshotAI/MoonEP), an MIT-licensed expert-parallel communication library; and
- [AgentENV](https://github.com/kvcache-ai/AgentENV), an MIT-licensed distributed system for running and resuming agent sandboxes at scale.

That surrounding infrastructure matters. A model architecture is useful only if somebody can execute it efficiently. Kimi Delta Attention needs specialized kernels. A sparse model with hundreds of experts needs a way to route tokens across accelerators without one overloaded expert slowing every other device. Long-running coding agents need environments that can pause, resume, fork, and retain filesystem state.

The release therefore exposes three different layers:

```text
Model intelligence      Kimi K3 weights and technical report
Inference machinery     FlashKDA + vLLM/SGLang/TokenSpeed support
Agent infrastructure    MoonEP communication + AgentENV sandboxes
```

The weights receive the headlines. The infrastructure determines whether the weights become a usable ecosystem rather than a 1.56 TB museum exhibit.

There are still important things Moonshot did **not** release. The complete pre-training dataset is not available. The report describes training methods, reinforcement-learning environments, and infrastructure, but it is not a fully reproducible recipe that lets another lab recreate K3 from raw data. Open weights give outsiders the trained artifact; they do not expose every decision that produced it.

## How can a 2.8-trillion-parameter model use only 104 billion parameters?

Kimi K3 is a **Mixture of Experts**, or MoE, model. The simplest way to understand MoE is to separate the model's total knowledge capacity from the amount of machinery used for one token.

A conventional dense model uses essentially the same parameter blocks for every token. An MoE model contains many specialized feed-forward blocks called experts. A router scores those experts and sends each token through only a small subset.

K3 has 896 routed experts. It selects 16 for each token, with two additional shared experts. The routed fraction is only about **1.8% of the expert pool** at a time.

```text
Incoming token
      │
      ▼
┌──────────────┐
│ MoE router   │ scores 896 routed experts
└──────┬───────┘
       │ selects 16
       ▼
┌────┬────┬────┬─────────┬────┐
│ E7 │ E42│ E91│   ...   │E811│  + 2 shared experts
└────┴────┴────┴─────────┴────┘
       │
       ▼
Combined representation → next layer
```

This is why both of these statements can be true:

1. Kimi K3 contains 2.8 trillion parameters.
2. It activates 104 billion—about **3.7% of the total**—for a token.

The benefit is sparse computation. K3 can increase total model capacity without paying the arithmetic cost of a dense 2.8T model on every token.

But sparse computation is not sparse ownership. The router can choose different experts for the next token, request, or user. All expert weights must remain available somewhere in the serving system. You cannot keep only today's 16 experts and delete the remaining 880; the next token may need a different combination.

A restaurant analogy helps, as long as we do not stretch it too far. One meal may use only 16 specialists, but the restaurant still needs the full kitchen because the next order can require another team. MoE reduces how many cooks touch one plate. It does not shrink the building.

### Three architectural ideas behind K3

MoE is only one part of the design. The report organizes K3 around information flow across sequence length, network depth, and model width.

**1. Kimi Delta Attention across sequence length.** KDA is a recurrent, linear-attention mechanism intended to process long sequences more efficiently than applying full quadratic attention at every layer. K3 interleaves three KDA layers with one Gated Multi-head Latent Attention layer. The periodic global-attention layers retain unrestricted token-to-token interaction.

**2. Attention Residuals across depth.** A conventional residual stream repeatedly accumulates each layer's output. Attention Residuals let a layer selectively retrieve representations from earlier blocks instead of accepting the entire history with equal weight. Think of it as giving depth its own retrieval mechanism.

**3. Stable LatentMoE across width.** K3 scales to 896 routed experts while trying to keep routing and training stable. MoonEP addresses a related systems problem: if too many tokens select experts on one accelerator, that device becomes the bottleneck. Its dynamic redundant-expert design aims to keep the work balanced across ranks.

Moonshot says these changes, together with its training and data recipes, deliver roughly **2.5 times better scaling efficiency than Kimi K2**. That wording matters. It is a company-reported scaling-law result about capability gained per training compute. It does **not** mean K3 is automatically 2.5 times faster or cheaper to serve.

## Why a sparse model still weighs 1.56 TB

K3 uses quantization-aware training with **MXFP4 weights** and **MXFP8 activations**. Four-bit weights are a major reason a 2.8T-parameter checkpoint can fit into roughly 1.56 TB rather than several terabytes more.

Yet four bits multiplied by 2.8 trillion parameters is already about 1.4 TB before accounting for scales, metadata, non-weight files, and format overhead. Compression makes the release possible. It does not make it small.

The runtime also needs more than static weight storage:

- memory for active computations;
- recurrent and attention state;
- buffers for expert routing and cross-device communication;
- image representations for multimodal requests;
- cache or state for long conversations;
- and capacity for concurrent users.

The advertised one-million-token context window makes the systems problem harder. Maximum context is not free memory, instant prefill, or perfect recall. A provider must ingest the prompt, maintain the model's state, schedule work, and decide what can be cached. Long agent sessions also branch, call tools, retry failed actions, and append large tool outputs.

Moonshot's [official blog](https://www.kimi.com/blog/kimi-k3) recommends deploying K3 on supernode configurations with **64 or more accelerators** because inference benefits from a large high-bandwidth communication domain. That is a recommendation, not a formally published minimum. Creative operators will try slower storage offloading, unusual quantizations, fewer devices, and expert streaming. The trade-off will be latency, throughput, context capacity, or all three.

The early [r/LocalLLaMA launch thread](https://www.reddit.com/r/LocalLLaMA/comments/1v8364f/kimi_k3_weights_now_released/) captured the problem perfectly. The most popular joke was: **"How do I download RAM in Hugging Face?"** Underneath the joke were serious debates about multi-node B200/B300 systems, storage capacity, tokens per second, and whether self-hosting could ever beat paying an inference provider.

Those comments are useful signals, not benchmark data. Hardware prices and throughput estimates posted during launch-day excitement should not be repeated as facts without measured deployments. The reliable conclusion is narrower: **K3 is datacenter-class software today.**

## Downloadable, local, and open source are three different claims

AI discussions often compress three separate ideas into one word: *open*.

| Question | What it means | Kimi K3 |
| --- | --- | --- |
| Can I download the trained parameters? | Open weights | Yes |
| Can a typical developer run it privately on local hardware? | Local accessibility | No, not realistically at full scale today |
| Can I reproduce, modify, and redistribute the complete system under a standard open-source license? | Open-source reproducibility | Not fully |

Moonshot repeatedly calls K3 an open-source model in its product documentation. The more precise description is **open weight with a custom license**.

The [Kimi K3 License](https://huggingface.co/moonshotai/Kimi-K3/blob/main/LICENSE) grants broad rights to use, copy, modify, merge, publish, distribute, sublicense, sell, deploy, and fine-tune the software and weights. It then adds commercial conditions that standard permissive licenses such as MIT or Apache 2.0 do not contain.

The two conditions most businesses need to notice are:

1. If a company operates a model-as-a-service business and it or its affiliates exceed **$20 million in aggregate revenue over any consecutive 12 months**, it must reach a separate agreement with Moonshot before using K3 commercially.
2. If a commercial product using K3 exceeds **100 million monthly active users** or **$20 million in monthly revenue**, the product must prominently display "Kimi K3" in its interface.

Internal use and access through Moonshot's official products or certified partners receive exceptions described in the license.

This does not make the release meaningless. Most individual developers, researchers, startups, and internal enterprise deployments gain broad rights. But "anyone can download it" is not the same as "anyone can use it for any purpose without additional conditions."

The distinction matters because licensing determines who can build a competing API business—the exact group best equipped to operate a 1.56 TB model. The release opens the weights while preserving leverage over large commercial serving companies.

A concise description is:

> Kimi K3 is openly downloadable, commercially conditional at scale, and operationally inaccessible to ordinary local hardware.

That is less exciting than "frontier AI is now open source," but it is more accurate.

## Does Kimi K3 actually compete with proprietary frontier models?

Moonshot's strongest claim is not model size. It is that an open-weight model now operates near the proprietary frontier across coding, reasoning, visual work, and long-running agents.

The company's own technical report is unusually direct about the limit: K3 **still trails Claude Fable 5 and GPT-5.6 Sol overall**. Its position changes by benchmark.

| Benchmark | Kimi K3 | Claude Fable 5 | GPT-5.6 Sol | What the table suggests |
| --- | ---: | ---: | ---: | --- |
| DeepSWE | 67.5 | 70.0 | 73.0 | K3 trails both |
| Terminal-Bench 2.1 | 88.3 | 88.0 | 88.8 | Near parity |
| ProgramBench | 77.8 | 76.8 | 77.6 | K3 narrowly leads |
| FrontierSWE | 81.2 | 86.6 | 71.3 | Between the two |
| SWE-Marathon | 42.0 | 35.0 | 39.0 | K3 leads this evaluation |

These are reported results, not a controlled experiment proving one model is universally better. The [benchmark footnotes](https://www.kimi.com/blog/kimi-k3) reveal why:

- K3 often uses the Kimi Code harness;
- other models may use Claude Code, Codex, Terminus, or whichever harness produced their best result;
- all K3 results use maximum reasoning effort;
- some Fable 5 runs may include fallback behavior;
- some GPT-5.6 Sol runs may encounter cyber guards;
- several comparisons cite external leaderboards while others were run by Moonshot;
- and Kimi Code Bench is an internal benchmark.

A coding agent is the combination of a model, prompt, tools, context manager, sandbox, retry policy, and token budget. Change the harness and you change the system being measured. Comparing models under different harnesses may reflect the product a user can actually access, but it does not isolate raw model quality.

The honest launch-day conclusion is therefore:

- K3 has credible evidence of frontier-adjacent performance;
- it wins some reported evaluations and loses others;
- Moonshot's own report does not claim it is best overall;
- and independent same-harness replication is still needed.

### An independent check from UK AISI and CAISI

The most useful independent evidence available at launch comes from the [UK AI Security Institute and the U.S. Center for AI Standards and Innovation](https://www.aisi.gov.uk/blog/preliminary-assessment-of-kimi-k3s-cyber-capabilities). Their preliminary evaluation examined offensive cyber capabilities before the weight release.

The result was mixed:

- K3 scored **32% on ExploitBench**, above GLM-5.2 at 24%;
- it achieved arbitrary code execution on **0 of 41** ExploitBench samples, while the most capable closed models averaged 20 of 41;
- on a 32-step simulated corporate-network attack, K3 reached step 17 on average, compared with 11 for GLM-5.2 and 28.5 for the leading closed models;
- it completed the full simulated attack in 1 of 10 attempts;
- and its safeguards did not prevent it from attempting offensive cyber operations in the evaluation.

This does not settle K3's general capability. The assessment was preliminary and covered a selective set of cyber tasks. It does provide something the launch benchmarks cannot: an evaluator other than Moonshot finding the same broad pattern—**K3 advances the open-weight frontier, but a measurable gap remains on difficult tasks.**

It also raises a security question familiar from [MCP and tool-calling agents](/blog/ai-agents-mcp-security-crisis): once capable weights are downloadable, provider-side safeguards are no longer a durable control boundary. Defenders gain a model they can inspect and run privately. Attackers gain the same permanence and configurability.

## Why do the weights matter if you cannot run them at home?

This is where the release becomes more than a record-setting file transfer.

### 1. Inference providers can compete with the creator

A closed model has one official seller. The provider controls price, regions, rate limits, retention policies, safety behavior, and deprecation.

Open weights allow independent operators to compete on:

- price per token;
- latency and geographic location;
- privacy and data residency;
- context limits;
- quantization;
- fine-tuning;
- tool-use policies; and
- service reliability.

Most developers may still call an API, but they no longer have to call **one specific API**.

Moonshot's official service launched at **$0.30 per million cache-hit input tokens, $3 per million cache-miss input tokens, and $15 per million output tokens**. Those prices are a snapshot, not a permanent property of the model. Once more providers deploy K3, the market can test how much of that price reflects compute, utilization, software quality, or margin.

### 2. Enterprises can keep control of sensitive workloads

A bank, hospital, government agency, or large software company may care more about control than local affordability. Running K3 inside an approved environment can offer:

- data that does not leave the organization's infrastructure;
- fixed model versions for auditability;
- predictable retention policies;
- custom security controls;
- and freedom from unilateral API deprecation.

That does not mean self-hosting is automatically cheaper. Accelerators are only the beginning. A production deployment needs networking, cooling, power, observability, failure recovery, model engineers, and enough demand to keep expensive hardware utilized. Idle GPUs can make a theoretically cheap token extremely expensive.

The [Hacker News technical-report discussion](https://news.ycombinator.com/item?id=49070985) centered on exactly this trade-off. Commenters proposed aggressive cost estimates for large racks, while others pointed out staffing, colocation, liquid cooling, concurrency, and idle capacity. Both sides can be right for different utilization curves.

### 3. Researchers can inspect a stable artifact

An API is an experience. Weights are an artifact.

With the checkpoint, researchers can study activations, routing behavior, quantization, long-context failure, safety tuning, model editing, and fine-tuning. They can test the same revision months later. They can preserve it even if Moonshot changes the hosted product.

That permanence is easy to underestimate. Closed providers can silently update system prompts, safety filters, routing, context management, or the underlying model while keeping the same product name. A downloaded checkpoint can be hashed, archived, and evaluated repeatedly.

### 4. K3 can become a parent, not just a product

The full model may be too large for consumers, but it can generate training data, supervise smaller models, and support distillation or specialist fine-tuning. The most important downstream result may be a smaller model that does not exist on launch day.

Open-weight ecosystems often compound this way:

```text
Large released checkpoint
        ↓
Independent evaluation and serving work
        ↓
Quantizations, fine-tunes, distillations, adapters
        ↓
Smaller and more specialized deployable models
```

K3's 1.56 TB size is therefore both a limitation and a source asset. The original model is difficult to operate. Its outputs, architecture, and learned representations can still seed systems that are easier to deploy.

### 5. Capability cannot be withdrawn

A downloadable model cannot be fully recalled because a vendor changes strategy, a product fails, or a regulator pressures one endpoint. Access can become difficult; repositories can disappear; licenses can be disputed. But once the files are widely copied, the capability persists.

That persistence is valuable for scientific reproducibility and operational continuity. It is also why releasing capable weights creates a different security profile from exposing the same model through a monitored API.

## The real shift is from model monopoly to infrastructure competition

K3 does not eliminate centralization. It changes where centralization happens.

With a proprietary model, control concentrates at the model lab. With a 1.56 TB open-weight model, control can spread across multiple hosting companies and large enterprises—but it still concentrates around organizations that own accelerators, high-bandwidth networking, power, and inference expertise.

```text
Closed model
User → one model vendor → one policy and price surface

Kimi K3 weights
User → competing inference providers → same base weights, different services
                         └──────────→ private enterprise clusters
                         └──────────→ research and downstream models
```

The bottleneck moves through the stack:

| Closed-model bottleneck | Open-weight K3 bottleneck |
| --- | --- |
| Permission to access the model | Ability to obtain enough compute |
| One provider's price | Provider competition and utilization |
| One safety and policy layer | Operator-specific controls |
| Vendor-controlled model lifecycle | Infrastructure and maintenance burden |
| Limited inspection | Deep access, but incomplete training provenance |

This is still a meaningful redistribution of power. A market with ten K3 providers is structurally different from a market with one K3 endpoint, even if an individual developer rents tokens in both cases.

The lesson is not that open weights failed because the model does not fit on a gaming PC. "Local AI" and "competitive model markets" are different goals. K3 advances the second far more than the first.

For engineers designing large AI products, this turns model routing into an architectural choice rather than a permanent vendor marriage. The capability-aware routing ideas in my [million-user AI chat system design](/blog/ai-chat-system-design-million-users) become more practical when several operators can serve the same base model under different latency, privacy, and price profiles.

## What we still do not know

Launch day is the worst time to confuse available numbers with settled truth. Several questions need real deployments and independent evaluation.

### Real serving performance

We need end-to-end tokens per second, time to first token, prefill latency, and cost under realistic agent workloads. A single-user decode benchmark does not tell us how K3 behaves with concurrent long-context sessions, tool outputs, retries, and branching trajectories.

### Minimum viable hardware

Moonshot recommends 64 or more accelerators, but operators will test smaller clusters, offloading, lower-throughput configurations, and future quantizations. "Can boot" and "can serve economically" are different standards.

### One-million-token quality

We need tests of retrieval, reasoning, instruction retention, and contradiction handling across the full window. The official report warns that generation can become unstable if a harness fails to preserve K3's complete thinking history or switches models mid-session.

A context-window number measures accepted input length. It does not measure how well every part of that input influences the answer.

### Same-harness model comparisons

The launch table mixes harnesses and evaluation sources. Strong conclusions require repeated tests with the same prompts, tools, sandbox, context policy, reasoning budget, and correctness criteria.

### Router behavior after post-training

An MoE system lives or dies by routing. Independent operators need to understand expert-load distribution, specialization, hot experts, communication overhead, and whether post-training creates pathological imbalance on real traffic.

### License interpretation

The custom thresholds are readable; their application to affiliates, derivative models, unusual service structures, and cross-border businesses may still require legal analysis. Downloadability does not remove license risk.

### Security after unrestricted adaptation

The UK AISI/CAISI evaluation tested a hosted pre-release system. Open weights let operators alter prompts, post-training, scaffolding, budgets, and safeguards. Defensive and offensive capability may look different once independent teams optimize the complete system.

These unknowns are not reasons to ignore the release. They are reasons to resist turning a model card into a verdict.

## Who should care right now?

**Individual developers:** use a hosted K3 service if its quality, privacy terms, and price fit your work. Do not buy hardware for the full model based on launch-day estimates.

**Local-LLM enthusiasts:** watch for expert streaming, quantizations, distillations, and smaller derivatives. The full checkpoint is more useful as an ecosystem parent than a workstation target.

**Enterprises:** compare total cost of ownership, not GPU cost alone. Include concurrency, utilization, staffing, networking, cooling, failure recovery, licensing, and the value of data control.

**Researchers:** the weights, report, and supporting infrastructure create a rare opportunity to study a near-frontier MoE system beyond an API boundary.

**AI product teams:** treat open weights as leverage. A portable model option can improve negotiating power and reduce dependency even when a third party still hosts the inference.

## Open weights did not remove the gate. They moved it.

Kimi K3 is not the best model on every benchmark. It is not reproducible from an entirely open training pipeline. Its custom license is not unrestricted. It will not run usefully on a normal developer workstation. Moonshot says as much about the performance gap, while the repository and license make the other limitations visible.

And yet the release matters.

A 2.8-trillion-parameter, native multimodal, long-context model with credible frontier-adjacent coding and agent capability can now be downloaded, archived, inspected, modified, independently hosted, and used to train what comes next. No single API provider has exclusive technical custody of that artifact.

The phrase "democratizing AI" is too imprecise for what happened. K3 did not make frontier inference equally affordable. It widened the set of institutions that can own and operate the capability, and it gave researchers and downstream builders raw material they did not have before.

**Kimi K3 did not put a frontier model on every desk. It put one outside the walls of a single AI lab—and made compute, rather than permission, the next gatekeeper.**
