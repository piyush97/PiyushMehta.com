Your application still starts. Your tests still pass. The Docker image still builds. None of those things tell you whether the interpreter underneath it will receive another security fix.

**Python 3.10 reached end of life on October 1, 2026.** The [official release announcement](https://blog.python.org/2026/10/python-31022-31117/) names **3.10.22 as its final release** and says the series will receive no further security updates. Installing that final patch does not extend its support window.

This is the useful question behind the release news: **which Python actually runs your application, who maintains it, and how do you replace it without guessing about compatibility?**

> **The short answer:** Inventory deployed interpreters, choose a supported target your dependencies can run on, recreate environments, then test and roll out a new artifact. Updating packages with `pip` does not update Python.

The support table below is a snapshot checked on **October 5, 2026**, not a permanent promise about which patch is latest.

## What changed in the October Python releases?

The October 1 announcement covers five series: **3.10.22, 3.11.17, 3.12.15, 3.13.16, and 3.14.8**. Their version numbers look like a routine patch sweep. Their support implications are different.

| Python series | Upstream status on October 5, 2026              | What that means for an upgrade                                                      |
| ------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------- |
| 3.10          | End of life; 3.10.22 is the final release       | Move off the series; a final patch is not continuing support                        |
| 3.11          | Security fixes only; scheduled EOL October 2027 | Still supported, but offers a shorter support runway                                |
| 3.12          | Security fixes only; scheduled EOL October 2028 | A possible compatibility-driven target, not the newest maintenance branch           |
| 3.13          | Security fixes only; scheduled EOL October 2029 | 3.13.16 was the last full maintenance release, including binary installers          |
| 3.14          | Bugfix maintenance; scheduled EOL October 2030  | A reasonable target to evaluate when dependencies and deployment tooling support it |

Sources: [Python's version-status guide](https://devguide.python.org/versions/) and the [October release announcement](https://blog.python.org/2026/10/python-31022-31117/). The future EOL months are scheduled dates and can change.

There is another distinction worth keeping straight: **support status is not installer availability**. Python 3.11 and 3.12 still receive upstream security fixes, but the announced 3.11.17 and 3.12.15 releases are source-only. Python 3.10.22 is also source-only, and that series is now unsupported.

A missing Windows or macOS installer does not mean every series in the announcement is EOL. An available installer does not guarantee years of full maintenance ahead.

## Step 1: Find the Python you actually deploy

Do not stop at the version on your laptop. Check the application container, worker image, scheduled job, CI runner, and production process separately.

Run these commands **inside the environment being inspected**:

```bash
python -VV
python -c "import sys; print(sys.executable); print(sys.version)"
python -m pip --version
```

The executable path helps distinguish a system interpreter from a project environment. Using `python -m pip` associates the package tool with that interpreter instead of whichever standalone `pip` happens to be on your shell's path.

The standard library documents [`sys.executable`](https://docs.python.org/3/library/sys.html#sys.executable), [`sys.version`](https://docs.python.org/3/library/sys.html#sys.version), and the [`-VV` option](https://docs.python.org/3/using/cmdline.html#cmdoption-V). If your environment uses another executable name, substitute that interpreter explicitly.

Record three things for each deployed workload:

- **Interpreter and provenance:** Python version, executable path, container base image or operating-system package.
- **Dependency contract:** The project's lockfile or dependency manifest, including native extensions.
- **Owner and deployment path:** Who can rebuild, test, and replace the running artifact.

The version in `pyproject.toml` describes a constraint. It does not prove what an already-deployed process is running. Likewise, upgrading a host's Python does not necessarily replace Python inside a container built months earlier.

<details>
  <summary>My Linux distribution still supports its Python 3.10 package. Am I unsupported?</summary>

**Upstream CPython support and distribution support are separate contracts.** A vendor may backport fixes under its own policy. Check the exact distribution release, package, advisory history, and support entitlement.

The upstream EOL notice does not establish that your vendor has stopped maintaining its package. It also does not establish that your vendor is maintaining it. Record the evidence rather than inferring either answer from the minor version.

</details>

## Step 2: Choose a target your application can prove

Evaluate the latest supported maintenance series first. As of this snapshot, that is Python 3.14. **Treat it as a candidate, not a compatibility guarantee.**

Your framework, database driver, numerical stack, monitoring agent, and deployment platform may constrain the move. A package publishing a compatible wheel matters when your build environment cannot compile an extension. A successful install matters, but is not the same as a successful application test.

If a dependency prevents the preferred target, make the fallback explicit: a supported series, a reason, an owner, and a date to revisit it. Moving from 3.10 to 3.11 buys upstream support time; it does not buy the same runway as a later supported series.

Read the target's migration notes, including [Python 3.14's porting section](https://docs.python.org/3.14/whatsnew/3.14.html#porting-to-python-3-14), alongside your dependencies' release notes. When crossing several versions, review the intervening changes too. Do not assume code that passed on 3.10 behaves identically after four minor-version changes.

<details>
  <summary>Should I jump through every Python version in production?</summary>

Not necessarily. A direct move to a supported target can be reasonable when your dependencies support it and your tests cover the relevant behavior.

Testing an intermediate interpreter can help isolate a compatibility failure. That is a debugging technique, not a requirement to deploy each version along the way.

</details>

## Step 3: Recreate the environment, then test the application

A virtual environment is based on the interpreter that created it. The [`venv` documentation](https://docs.python.org/3.14/library/venv.html) describes environments as disposable and explains why they should be recreated rather than moved or copied.

Build a **separate target environment** from the project's dependency contract. Keep the currently working deployment intact while you evaluate the replacement.

For a POSIX project that already uses `requirements.txt` and pytest, the shape is:

```bash
# Assumes Python 3.14 is installed and pytest is a declared test dependency.
python3.14 -m venv .venv-314
.venv-314/bin/python -m pip install -r requirements.txt
.venv-314/bin/python -m pip check
.venv-314/bin/python -m pytest
```

This is an illustrative workflow, not a universal installer. Use your repository's lockfile-aware installer and test command when they differ. Verify the chosen interpreter's patch version too; `python3.14` alone does not establish that it is current.

<details>
  <summary>Show the equivalent PowerShell commands on Windows</summary>

This example assumes the Python launcher can select an installed Python 3.14 interpreter, and the project has the same `requirements.txt` and pytest setup.

```powershell
py -3.14 -m venv .venv-314
.\.venv-314\Scripts\python.exe -m pip install -r requirements.txt
.\.venv-314\Scripts\python.exe -m pip check
.\.venv-314\Scripts\python.exe -m pytest
```

Calling the environment's interpreter directly avoids depending on shell activation. See the [Windows launcher documentation](https://docs.python.org/3/using/windows.html#python-launcher-for-windows) for interpreter selection.

</details>

`pip check` checks installed dependency compatibility. It does **not** test application behavior, audit every vulnerability, or prove that a native extension works with your production data.

Put the old and candidate runtimes through the same meaningful checks: unit tests, integration tests, application startup, database connections, serialization boundaries, background jobs, and your critical request paths. During the migration, an old-runtime CI lane is a useful comparison. Once the migration is complete, remove it from the supported matrix rather than accidentally advertising ongoing 3.10 support.

## Step 4: Roll out an artifact, not a version string

For containers, update the base image, rebuild dependencies, run checks against the resulting image, and deploy that image. Editing a Dockerfile without rebuilding does not change running containers.

For managed platforms, verify the runtime configured in the deployment system and the runtime reported by the deployed application. For operating-system packages, follow the platform's supported application deployment path; do not replace a system interpreter blindly.

A staged rollout needs a clear success signal: application health, error rates, worker failures, and whichever business operation the service exists to perform. Compare the candidate with your current behavior rather than accepting "the process started" as the finish line.

Keep a known-good artifact available during the transition. **Code rollback does not automatically reverse a database or data-format change.** If the runtime upgrade is bundled with a schema change, evaluate that compatibility separately; the [zero-downtime database migration guide](/blog/zero-downtime-database-migration-at-scale) covers that adjacent deployment problem.

## Python 3.10 EOL FAQ

### Does end of life mean my application will stop working?

No. It means upstream Python 3.10 maintenance has ended. Existing programs can continue running; that is not evidence that the runtime will receive future security fixes. Vendor-maintained packages need their own support-policy check.

### Is Python 3.11 still supported?

Yes, in security-fix-only mode as of this article's October 5 snapshot, with EOL scheduled for October 2027. The announced 3.11.17 patch is source-only. Support and official binary installers are separate questions.

### Is updating to Python 3.10.22 enough?

It gets you to the final upstream release. It does not remove the need to migrate to a supported interpreter or establish a separately maintained vendor package.

### Which Python version should I upgrade to?

Evaluate the current supported maintenance series, then verify your dependency and deployment compatibility. At this snapshot, Python 3.14 is the maintenance-series candidate. If it does not work for your application yet, document a supported fallback and a follow-up plan rather than declaring compatibility without tests.

## The decision to make this week

The release announcement gives you a deadline fact, not an application migration result. Turn it into a small, owned piece of work: identify every deployed 3.10 interpreter, establish who maintains it, choose a supported target, and test the artifact you intend to ship.

**A passing application is one signal. A maintained runtime is another. You need both.**
