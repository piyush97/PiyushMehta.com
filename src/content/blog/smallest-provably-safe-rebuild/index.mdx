Someone changes a TTL. Nothing about the record's value moves, nothing gets signed differently, and one integer in one row is different. In 2022 that event started a build that read every record in the zone, encoded all of them, compared all of them against what was already stored, and held the whole zone in memory while doing it.

On a zone with 20 million records, the work is unrelated to the change. That is the definition of a bad unit of recomputation, and it has a second cost people forget: the build sits on a Kafka partition. While it retries, every other zone sharing that partition waits behind it.

Cloudflare [published the fix on November 2, 2026](https://blog.cloudflare.com/dns-targeted-zone-builds/): 92.95% of builds now skip the complete zone, full builds fell from 11.88% to 7.04%, and the worst p99 build-completion delay dropped from 14.6 minutes to 1.21. Their memory working set went from 49 GiB average to 7. What makes the post worth reading is not the numbers. It is that almost all the effort went into _proving_ the smaller build was safe, not into making it faster.

## What a build actually does

The Zone Builder turns database state into the keys the authoritative DNS servers read from Quicksilver. A full build reads the zone and every record in it, converts each record into a key, diffs against what is stored, then removes stale keys, writes changed keys, and updates zone metadata. The final write is already small. The read is the whole zone.

For record changes, Cloudflare had already fixed this in a [2022 post](https://blog.cloudflare.com/dns-build-improvement/). That post closed with the obvious next step: do the same thing for zone settings. It also left the exact bug that makes this hard. Their first targeted implementation wrote the _new_ record but did not delete the old key when a record's name changed, so old names kept resolving. The build had no way to know which key to remove, because the event carried only the new record. The fix was to make the producer emit a create and a delete. Nobody had described the delete as part of the change set, and the change set is the whole problem.

It took until November 2026 to do the same for settings, because a record event names a key and a setting does not. Toggling Universal SSL updates metadata and can also change CAA records at the apex, because CAA is what tells certificate authorities whether they may issue for your domain. Enabling a zone on a new network changes what is published at all.

So the interesting question is not "how do we rebuild less." It is: **which keys can this event possibly change, and how do you know you got the list right?**

## The proof obligation

Strip the domain away and there is one claim:

> For event `e` and zone `z`, the targeted build writes exactly the keys a full build would have written, with exactly the same values.

Everything else is bookkeeping. If that holds, the smaller build is not an approximation of the full one; it is the same build with a shorter input. If it does not hold, the difference is a stale key, which is the worst failure shape in computing: silent, unbounded in time, and invisible to any test that only checks the keys you did rebuild.

Cloudflare's planner answers three questions per event: which DNS names can change, whether shared metadata or the published-zone list can change, and what previous state must be removed. To answer them, events had to start carrying the changed fields and settings with old and new values, and each setting had to be traced through the code that generates DNS output and classified by what it can affect.

The rule that does most of the work is boring and correct: **uncertainty never turns into less work.** Some database functions only update a timestamp, which looks identical to "something changed, search the zone." Until the producer can say which fields differ, that event buys a full rebuild. Unknown events, missing details, and anything that might touch records anywhere in the zone all escalate the same way.

Merging amplifies the same rule. The unified scheduler combines queued work per zone, and combining only ever adds: if any one event needs the full zone, the merged build is a full build; a purge (the zone should no longer be published here) overrides every rebuild. Work merges upward, never downward. That is the property that lets you combine 700 record changes per second plus 100 settings events per second without writing a merge rule that quietly loses a key.

## The exception they wrote down

Here is the part most engineering write-ups would leave out. A full build holds every record and every stored key for the zone in memory at once. For the largest zones, that set does not fit. So above a fixed record-count threshold, the Zone Builder **never escalates to a full build**, even when the planner says it should. It rebuilds the apex, the metadata, and every name the queued events identified, and accepts that this is not equivalent to a full build.

That is a deliberate, bounded unsoundness in a correctness-critical path, and the justification is a queue argument rather than a correctness argument: a full build of those zones cannot finish, and while it retries it holds back every other change on its Kafka partition. A build that is theoretically correct and blocks a shared resource forever is not the safer choice. They reduce the exposure (name holds stop two accounts from holding the same name, which removes many of the multi-zone cases) and keep a manual path to rebuild individual names for the rest.

Two things make this survivable instead of reckless. It is bounded to zones above a stated size. It is written down where the next engineer will read it. If you ship an incremental system, you will eventually have the same choice. Decide the threshold, decide what the degraded path does, and put both next to the code.

## Testing a claim about all inputs

You cannot unit-test "the closure is complete." You can only test it against a second implementation and a lot of real inputs. Cloudflare runs a mirror Zone Builder that consumes the production Kafka stream and reads production database state, but writes to a separate Quicksilver environment that serves no customer traffic. A comparer samples 20% of zones and looks for missing keys, extra keys, and different values.

The measurement detail matters more than the setup. The two pipelines do not build a zone at the same instant, so a per-zone mismatch is usually just skew, not a bug. Reporting "0.31% diff rate across 234,313 matched zones" as a health metric would be misleading in both directions: too alarming on a normal day, and too calm on the day a new _kind_ of difference appears. So the dashboard groups differences by type, keeps examples, and the alert condition is a new class of difference that survives after both pipelines catch up.

That is the right metric for a differential test. Novelty of failure mode beats frequency of failure, because frequency is dominated by timing noise you already understand.

There is also a race the mirror inherits: Kafka delivery and database replication move independently, so an event can arrive before its change is visible on the replica the build reads. The aggregator holds events long enough to cover normal lag, and the build does a final database check that rejects a read from a replica that is still behind. Event-driven systems that read their own write need both halves: a delay that is usually enough, and a check that is always enough.

## Rolling out a scheduler change

The rollout deserves a paragraph because it is the kind of detail that decides whether a correctness change survives contact with production. They split traffic by a hash of the **zone name**, not the zone ID, so every zone sharing a name lands on the same scheduler and two schedulers never write the same metadata key. Then they ramped by plan, starting with free zones.

Note what that buys: the old and new schedulers coexist for days, so the failure mode of a bad split is not "two writers, one key" but "traffic moves back." Any migration that changes who writes a shared key needs a partition function that respects the sharing, not just a percentage.

## The result, and where the cost actually was

Over 24 hours: 86.81% of builds touch resources only, 2.54% resources plus metadata, 2.30% apex plus metadata, 1.30% purges. Full builds are the remaining 7.04%, down from 11.88%, and the ones that remain average 0.35 s because they are mostly first publications of small new zones. For continuity: full builds were about 13% of all builds in 2022, and that 13% was settings changes of exactly this kind.

The delay number is the one I would put in front of a skeptical reviewer. The largest p99 spike in build-completion delay fell from 14.6 minutes to 1.21, a 12× reduction, measured by running the old schedulers in production and the unified scheduler in the mirror on the same events for the same 24 hours.

Read that measurement carefully, because the obvious interpretation is wrong. Typical delays barely moved in that comparison; almost all builds were already small, and the win is entirely in the tail. Median delay did halve later, from 7.7 s to 3.3 s, but that came from a second change: with full builds cheaper and rarer, they could safely shorten the per-zone rebuild interval and the aggregator's wait for replica lag. The scheduler fixed the spike; the interval guardrail fixed the median. Conflating the two would have you shipping the wrong fix.

Memory went from 49 GiB average and 79 GiB peak to 7 and 12. That is an 86% cut, and it is the part people underestimate: for a full build, working set scales with zone size, so the largest customers set your RAM bill and your OOM risk. Bounding the read to a closure bounds the working set to the size of the change. Incremental work is often sold as a latency win. At this scale it is a capacity decision.

## What to steal

- **Name the equivalence you are preserving.** Not "faster rebuild," but "same keys, same values as the full build." Without that sentence you cannot tell a bug from a design choice.
- **Derive the change set from emitted data, not from the event's name.** The 2022 rename bug existed because the delete was implied and never written down.
- **Make uncertainty cost more, never less.** Fail closed on unclassified input. A planner that guesses a narrow scope is a machine for producing silent staleness.
- **Keep the slow path and use it as an oracle.** The full build is not legacy to be deleted; it is the reference implementation your mirror compares against.
- **Watch for new kinds of diffs, not more diffs.** Sampling gives you detection, not proof, so the signal you can act on is a failure mode you have not seen before.

Your version of this is probably a cache invalidation path, an incremental index, a materialized view refresh, or a CDC pipeline. Same shape, same failure: the write you skipped is the key nobody rebuilt, and it will not page anyone.
