OpenAI released the [Decisions API in public beta on October 6, 2026](https://developers.openai.com/api/docs/changelog), powered by GPT-6 Luna. You may see it listed as `gpt-6-luna-decisions` by model routers. The interesting part isn't another chat model with a new name. It's a different API surface: give it evidence and typed questions, and get back decisions your application can consume.

That distinction matters for support teams. A chatbot can write, “This looks like a billing issue.” A routing system needs a queue name, a probability, and a policy for what to do when the evidence is weak. Luna Decisions is designed to return the former as structured data. Your code still owns the latter.

## What the Decisions API does

The public-beta Decisions API evaluates text, images, or both. Its documented endpoint is `POST /v1/decisions`, and `gpt-6-luna` is the model currently documented for it. A request contains a model, shared input, and one or more named questions. The question types include predicate, choice, and score. Those types let you ask whether a condition holds, select from a fixed set, or rate evidence against a rubric.

OpenAI describes this endpoint as returning typed answers and says it is about 10x faster than the Responses API. That's the vendor's comparison, not an independent benchmark or a promise for every workload. The API is in public beta, so check the current docs before depending on a particular contract in production.

The important separation is between a model answer and an application decision. A returned probability is useful evidence; it isn't a service-level guarantee, a calibrated confidence interval, or permission to skip review. Choose thresholds based on measured performance on your own ticket mix.

The three question types map to different kinds of work. A predicate is useful for a yes-or-no check, such as whether a message describes an account lockout. A choice fits routing because the allowed destinations are explicit. A score fits a rubric, such as urgency on a defined scale. You can ask more than one named question over the same input, which can avoid sending the same ticket through several separate model calls. Keep each question narrow enough that a support lead can explain what a correct answer means.

## Why use it for support triage?

Consider a ticket that says, “My renewal went through, but the dashboard still says trial.” A conversational model might produce a thoughtful explanation and ask follow-up questions. But before any reply, your help desk needs to know where the ticket belongs.

Ask for one choice from a small set: `billing`, `account_access`, or `technical_support`. Then let your application compare the top answer's probability with a threshold:

- Above threshold: send it to the selected team.
- Below threshold: place it in a human review queue.

The threshold is a policy knob owned by the product team, not a magic number emitted by the model. A stricter threshold trades more manual review for fewer uncertain automatic assignments. Start conservative, sample decisions, and adjust after reviewing real outcomes.

## A direct API request

The example below uses the public Decisions endpoint, not a chat-completions route. Keep the API key on a server and supply it through an environment variable. The question constrains the answer to a fixed choice set, while the ticket text remains the evidence.

```sh
curl --fail-with-body https://api.openai.com/v1/decisions \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-6-luna",
    "input": "My renewal went through, but the dashboard still says trial.",
    "questions": [
      {
        "name": "support_team",
        "type": "choice",
        "choices": [
          {"value": "billing", "description": "Payments, invoices, subscriptions, and refunds."},
          {"value": "account_access", "description": "Login, permissions, and workspace access."},
          {"value": "technical_support", "description": "Product errors and broken features."}
        ],
        "instructions": "Choose the team best suited to resolve this support ticket."
      }
    ]
  }'
```

Use a unique question `name` so you can associate each answer with the matching question. Choices are objects with a `value` and `description`, not an array of strings. For a real ticket, pass only the text needed to make the decision, and follow your normal privacy and retention rules. If these three categories do not cover your queue, add an `other` choice that always goes to review.

## Calling it from server-side JavaScript

You don't need to invent a new SDK method to try the endpoint. A server-side `fetch` call makes the HTTP contract explicit. This handler checks the HTTP status before parsing the result and lets the caller handle failures:

```js
export async function classifySupportTicket(ticketText) {
  if (typeof ticketText !== 'string' || !ticketText.trim()) {
    throw new TypeError('ticketText must be a non-empty string');
  }
  const apiKey = process.env.OPENAI_API_KEY;
  if (!apiKey) throw new Error('OPENAI_API_KEY is not set');

  const response = await fetch('https://api.openai.com/v1/decisions', {
    method: 'POST',
    signal: AbortSignal.timeout(10_000),
    headers: {
      Authorization: `Bearer ${apiKey}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      model: 'gpt-6-luna',
      input: ticketText,
      questions: [
        {
          name: 'support_team',
          type: 'choice',
          choices: [
            { value: 'billing', description: 'Payments, invoices, subscriptions, and refunds.' },
            { value: 'account_access', description: 'Login, permissions, and workspace access.' },
            { value: 'technical_support', description: 'Product errors and broken features.' },
          ],
          instructions: 'Choose the team best suited to resolve this support ticket.',
        },
      ],
    }),
  });

  if (!response.ok) {
    const detail = await response.text();
    throw new Error(`Decisions API ${response.status}: ${detail}`);
  }

  return response.json();
}

const decision = await classifySupportTicket(
  'My renewal went through, but the dashboard still says trial.',
);
console.log(JSON.stringify(decision, null, 2));
```

Save this as `luna-decisions.mjs`, set `OPENAI_API_KEY` in your server environment, then run `node luna-decisions.mjs` with Node.js 22 or later. It makes a real, billed API request; the interactive walkthrough below does not.

The API returns an `answers` array. Here is a **synthetic response excerpt**, adapted to our question, not a result from running the request:

```json
{
  "answers": [
    {
      "type": "choice",
      "name": "support_team",
      "choice": "billing",
      "probabilities": [
        { "value": "billing", "probability": 0.94 },
        { "value": "account_access", "probability": 0.02 },
        { "value": "technical_support", "probability": 0.04 }
      ],
      "confidence": 0.91
    }
  ]
}
```

Match the answer by `name`, then inspect its `type`. A `refusal` must go to review rather than being treated as a choice. For a choice answer, `choice` identifies the selected value, `probabilities` gives the per-option distribution, and `confidence` is a separate field. The walkthrough thresholds the selected option's probability, **not** `confidence`. Keep that distinction explicit in your production policy, and send missing or unexpected answers to review.

## What does it cost?

The [Decisions guide](https://developers.openai.com/api/docs/guides/decisions#pricing) lists **$0.10 per million input tokens** for `gpt-6-luna` on this endpoint, with no cache-read, cache-write, or output-token charges. At that base rate, 1,000 requests using 1,000 input tokens each cost $0.10. That is arithmetic, not a measured ticket workload: question instructions and descriptions also contribute to input size.

Regional processing premiums and long-context input multipliers apply. These are `/v1/decisions` prices, not the standard price for every GPT-6 Luna request. Recheck pricing before budgeting a rollout.

The threshold can differ by workflow, and the application can add other rules such as VIP status or regulated-content handling.

Measure before you automate. Review a representative sample of decisions, track wrong-team assignments and escalation rates, and pay special attention to tickets whose labels are ambiguous. If a wrong automatic route costs more than a quick human review, make the threshold stricter. Keep an override path, and record which policy version made each routing choice.

## Don't confuse the API with the router alias

The OpenRouter page for `openai/gpt-6-luna-decisions` is a separate product surface. Its model identifier is a router alias, not the `gpt-6-luna` model name documented for OpenAI's dedicated `POST /v1/decisions` endpoint. OpenRouter describes its routed interface using `state` as the evidence field and `noul` for a yes-or-no question. That schema isn't interchangeable with OpenAI's `input` and `questions` contract.

If you access the model through OpenRouter, use the router's own current endpoint, request format, and pricing page. If you need the typed Decisions API described here, use OpenAI's documented endpoint and schema. Don't copy a router alias into the OpenAI request and expect an equivalent response.

## What to verify before shipping

OpenAI's documentation describes Luna as the only model currently available on Decisions, and marks the API as public beta. The October 6 launch date comes from the official OpenAI API changelog. OpenAI's speed comparison is a published claim, not a latency guarantee; the demo makes no calibration claim. Check the live model and pricing pages for current availability and costs before estimating a rollout.

For an initial deployment, route a small share of tickets, retain a human fallback, and compare outcomes against your existing workflow. Once the results support expansion, raise the automated share gradually. Structured choices and probabilities make the policy easier to inspect, but the responsibility for safe, useful routing stays with the application.
